# CW Finance 十万级压力测试报告

> 测试日期：2026-09-19
> 测试人：Codex（压力测试专项）
> 压测工具：`scratch/glStressTest.mjs`（后端，可复现）+ Playwright 真实浏览器（前端）
> 核心问题：**十万级数据下，导入/导出/刷新/汇总会不会把服务器或浏览器卡死？**

---

## 一、一句话结论

**常规操作不卡，四种特定场景会卡死**：

| 场景 | 触发条件 | 后果 | 严重度 |
|---|---|---|---|
| 科目余额表缺日期参数 | `/ledger/general` 不带 start_date/end_date（如 `?year=2026`） | **SQL 同步执行 209 秒，期间整个后端 API 全部无响应**（better-sqlite3 同步阻塞，连登录都会卡住） | **P0** |
| 明细账单科目超大 | 明细账页单科目全年 ≥10 万行分录 | **浏览器主线程 >300 秒完全无响应（页面卡死）**，el-table 无虚拟滚动全量渲染 | **P0** |
| 导出超大数据 | 页面导出行数 ≥50 万 | 浏览器 JS 堆打满 OOM 崩页（10 万行实测堆 2,995MB，上限约 3,586MB，已 85%） | P1 |
| 批量记账运行期间 | 批量过账 3,000 张 | 主线程被同步过账占用 47~52 秒，**期间全后端 API 无响应** | P1 |

**不卡的部分（十万级实测）**：所有分页列表查询 <60ms、50 路并发明细账 P95=71ms、带日期的科目余额表 1.8s、服务端 xlsx 导出 8s、银行对账单 10 万行导入全链路 5.2s、批量审核 3,000 张 0.4s。

### 3.2 服务进程内存（RSS）

| 阶段 | RSS |
|---|---|
| 启动后 | 178MB |
| A 段轻查询后 | 190MB |
| 出纳日记账查询 ×6（每次全量拉 10 万行） | **427 → 647MB**（每次涨约 100MB，GC 后部分回落） |
| 科目余额表（前端口径）×3 后 | 175MB |
| 服务端 xlsx 导出后 | 1,149MB（ExcelJS 10 万行构建） |
| 出纳 10 万行导入 + 银行 10 万行落库后 | **1,379MB，且不再回落（全部完成后仍驻留 1,355MB）** |

> **进程不退出，但 1.3GB 内存长期驻留**——同类大导入做 2~3 次就有 OOM 风险（Node 默认堆上限约 4GB）。

### 3.3 两次完整跑的差异（重要发现）

| 轮次 | B 段科目余额表口径 | 结果 |
|---|---|---|
| 第 1、2 次 | `?year=2026`（缺日期参数） | **每次 194~209 秒；5 路并发含 2 个该查询时客户端 undici 300s 超时崩溃（ECONNRESET），压测中断** |
| 第 3 次 | 显式 `start_date/end_date`（前端真实默认口径） | 1.8 秒，全链路通过，不再崩溃 |

`year` 参数在 `/ledger/general` 端点**没有被读取**（routes/ledger.ts:155-189 只认 start_date/end_date），缺失时按「当月」拼区间反而触发慢计划——**这是一个任何调用方少传参数就会踩中的隐形雷**。

| 3 | fetchAllPages 拉 24.25 万行（25 页 × 1 万行，拉取+JSON.parse+数组展开） | **3.0 秒完成** | 169MB | 纯数据处理不是瓶颈 |
| 4 | 月度小计插入（全量变换 24.5 万行） | 30ms | 169MB | |
| 5 | 导出列矩阵解析（10 万行 × 10 列逐单元格） | 115ms | 169MB | |

**解读**：前端数据流水线本身（fetch/解析/变换）很快，**瓶颈是 el-table 全量渲染（无虚拟滚动）和导出期间多份数据并存**（el-table 数据源 + 变换后数组 + 矩阵三份同时存活，内存放大 18 倍）。

## 五、问题清单（按优先级）

### P0-1　科目余额表缺日期参数触发 209 秒全后端冻结

- **复现**：`GET /api/ledger/general?year=2026`（不带 start/end）。三次全量压测分别 196s / 232s（×3 次）/ 209s。
- **证据链**：
  1. 打点 `routes/ledger.ts:191` `db.prepare(query.sql).all()` —— SQL 执行占 99.99%（254,148ms / 254,163ms 总耗时）；
  2. 同库独立进程：显式全年日期 1.8s，**服务端默认参数（当月）208.7s**；
  3. EXPLAIN：显式全年时相关子查询走 `idx_voucher_entries_account (account_set_id, account_id)`（先定位科目再过滤日期）；缺参默认「当月」时计划劣化为 `idx_voucher_entries_voucher (voucher_id)`——对 954 个科目**逐个**走「日期范围→凭证→分录反查」，≈954 × 17.5 万分录次索引查找。
- **影响**：better-sqlite3 同步执行期间 **Node 事件循环完全冻结**——期间所有 API（含登录、任何页面）无响应 3.5 分钟；前端表现为全站转圈。若多用户并发触发（实测 2 路并发），客户端 300 秒超时直接断连。
- **修复建议**（三选一，推荐 ①+②）：
  1. **端点参数收口**：`/ledger/general` 强制要求 start_date/end_date（缺省时回退当年 1/1~12/31 并打日志），并把 `year` 参数纳入处理（前端传了 year 却被无视）；
  2. **SQL 改写**：8 个相关子查询合并为一次 CTE 聚合（`buildGeneralLedgerQuery` 的写法实测 1.6s，就是 `/ledger/general-ledger` 现在用的）；
  3. **加索引**：`(account_set_id, account_id)` 扩为覆盖 voucher_date 的物化月度汇总，或给 `voucher_entries(account_id, voucher_date)` 建索引并 `ANALYZE`。

### P0-2　明细账页单科目 10 万行 → 浏览器主线程 >300 秒无响应

- **复现**：明细账页选一个全年 10 万分录的科目（mock total=100,000）。`page.evaluate` 连续 300 秒无法返回（主线程被 el-table 全量渲染占死）；对照组 3,000 行时 10 秒渲染完成、JS 堆 527MB。
- **根因**：`Detail.vue` 的 `fetchDetailPayload` 用 `fetchAllPages(pageSize=10000)` **全量拉取后一次性 set 给 el-table**；el-table 无虚拟滚动，10 万行 × 10+ 列的 DOM/响应式开销直接锁死主线程。
- **修复建议**：
  1. 页面查询走服务端分页（el-table max-height + page-size≤500，需下钻再点「查看更多」）；
  2. 或接入虚拟滚动（el-table-v2 / vite-virtual-scroller），按现有 `useFillHeightTable` 模式补；
  3. 短期兜底：`total > 20,000` 时弹确认「数据量过大，建议缩小科目/日期范围或直接导出」。

### P1-1　出纳日记账查询无分页，全量拉取 10 万行

- **证据**：`cashierQuery.ts listJournal`（:303-309）`SELECT * ... WHERE 科目+币种 ORDER BY biz_date` **无 LIMIT**，10 万行全部进内存算逐行余额，路由（cashierJournal.ts:327-335）整体返回——页面只显示 100 行却传输 ~30MB JSON；每次请求 RSS 涨 100MB+（压测 A 段 6 次：427→647MB），耗时 544~673ms。
- **建议**：分页 + 窗口聚合（`LIMIT ? OFFSET ?`，余额用边界前的 SUM 一次性算出，窗口函数或首页全量读改为「期初 + 本页」口径）；前端 `Journal.vue` 已按 `data.list` 分页消费，改动小。

### P1-2　序时账导出预取 45 秒（24.25 万行）

- **证据**：25 页 × pageSize=10000，每页 ≈4.5 秒（含每页重复的 total COUNT + 1 万行取数+传输）。
- **建议**：① 导出模式复用一次 total（后续页跳过 COUNT）；② 大 total 时直接把筛选参数 POST 给服务端生成 xlsx（参考 `/export/styled-xlsx` 的 spec 机制改为「参数模式」），前端不再拉全量。

### P1-3　导出全链路 JS 堆 2,995MB（临界 OOM）

- **证据**：真实页面导出（序时账 24.25 万行）堆爬到 2,995MB 并持续 180 秒不落（上限 3,586MB）。
- **建议**：`exportStyledTableViaServer` 支持「筛选参数模式」（服务端查询+生成，见 P1-2）；或行数 >5 万时分 sheet/分段 POST 拼接；前端 `fetchAllPages` 加 `maxRows` 保护（如 20 万）与明确报错文案。

### P1-4　批量记账 3,000 张 = 52 秒全后端阻塞

- **证据**：batch-post-async 逐张同步过账（17ms/张 × 3,000 = 52 秒），期间事件循环被占——**批量记账跑着的时候，其他所有用户的请求全部排队**。对照组批量审核 0.4 秒无感。
- **建议**：过账循环每 50~100 张 `await new Promise(setImmediate)` 让出事件循环；或把过账事务批量化（单事务 500 张）减少 fsync（`synchronous=NORMAL` + WAL 下单张事务 fsync 仍是主要成本）。

### P1-5　10 万行导入后进程内存驻留 1.3GB

- **证据**：出纳导入 10 万行一次提交（7 秒）后 RSS 1,336MB；银行对账单落库后 1,379MB；**全部压测结束后仍驻留 1,355MB 不回落**。V8 未主动归还 + rows 数组/中间对象未释放。
- **建议**：导入路径改为「每 5,000 行一个事务 + 分批 JSON 解析」；导入完成后置空引用；超大数据建议前端分批提交（每批 ≤1 万行）并在 UI 上显示进度（项目已有 `TaskProgressDialog` 异步任务机制可复用）。

### P2（低优先）

- 银行对账单 confirm 把表头行也当数据行校验（errors 多 1 条「交易日期」，`header_row` 默认 -1 未跳过首行）；
- 序时账 `pageSize=100` 首页 1.4 秒（total COUNT + CTE 常驻），可加日期索引或缓存 total；
- 导出服务端 ExcelJS 构建 10 万行 8 秒 / 5.2MB 文件——合格但可 streaming 化（exceljs streaming workbook writer）降低峰值内存；
- multer 银行对账单限 20MB：10 万行 ≈16MB 已接近上限，约 12 万行会被 413 拒绝——建议改为流式或提高上限并提示。

## 七、对「会不会卡死」的最终回答

| 用户操作 | 十万级表现 | 卡死？ |
|---|---|---|
| 日常记账、翻列表、看账簿分页 | 全部 <60ms | 否 |
| 科目余额表（正常带日期） | 1.8s | 否 |
| 50 人同时查明细账 | P95 71ms | 否 |
| 余额表接口缺日期参数（前端某些入口清空日期/第三方调用） | **209s 全后端冻结** | **是** |
| 明细账单科目全年 10 万行 | **浏览器 >300s 无响应** | **是** |
| 页面导出 10 万行 | 堆 3GB，功能可用 | 临界 |
| 页面导出 ≥50 万行 | 预期 OOM 崩页 | 是 |

| 10 万行出纳/对账单导入 | 5~7 秒完成，数据完整 | 否（但内存驻留 1.3GB） |

## 八、复现方式

```bash
# 后端全量（约 6 分钟；含造数、查询、导出、导入、批量、并发）

# 只跑刷新+汇总段（快速复现 P0-1 与内存问题）

# 前端浏览器压测（临时 spec 已随报告归档思路，可按报告 §四 手工重建）
# 明细账 3,000 行 vs 100,000 行：对照组 10s/527MB，实验组 >300s 主线程死锁
```

## 九、修复优先级路线

1. **立即（P0）**：`/ledger/general` 参数收口 + 缺日期默认全年；general SQL 改 CTE 聚合写法（两处合计半天工作量）
2. **本周（P0/P1）**：明细账/序时账页面硬分页或虚拟滚动；`listJournal` 分页化；批量过账分片让出事件循环
3. **短期（P1）**：导出改「筛选参数→服务端生成」模式；导入分批事务 + 分批提交 UI
4. **排期（P2）**：序时账 COUNT 优化、exceljs streaming、multer 上限与提示、对账单表头行跳过

### 附：测试数据可信度说明

- 所有耗时为真实 HTTP 计时（非直连 DB），前后端同环境连续完成；
- 三次完整跑的关键数值（209s 慢计划、45s 全量拉取、7s 导入、52s 批量记账）复现一致；
- 服务端打点（`[perf-diag]`）与 EXPLAIN 计划差异可精确归因到 SQL 计划层，非环境噪声；
- 前端结论基于 Chromium 真实渲染（非 JS 模拟），`performance.memory` 与 `PerformanceObserver` 为浏览器原生指标。
