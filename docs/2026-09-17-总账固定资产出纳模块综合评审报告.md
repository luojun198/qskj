## 摘要

本轮共确认 **P0 级 4 项、P1 级 21 项、P2 级 19 项**。与历轮"逐个模块找缺陷"不同，本轮最大的发现集中在 **模块之间的边界**：

1. **三套期间闸口互不认账，形成两条互穿通道（P0-1 / P0-2）。**
   总账的 `period_closing`、出纳的 `cashier_period_closing`、固定资产（复用总账闸）三者在代码上**没有任何交叉引用**。结果是：出纳已结账的月份，其凭证在总账侧仍可被反记账、修改、反审核甚至冲红；反过来，总账已结账（甚至已年结）的期间，出纳仍能录入流水并生成新凭证。

2. **出纳模块是本轮风险最集中的模块。** 09-16 刚上线的结账功能本身逻辑正确，但闸口只挂在了 6 个入口上，另有 8 类会改动已结账月份数据的入口没有接闸；再叠加 SCM 收付款单直接写/删 `cashier_journal`（完全不经过出纳路由），"已结账 = 冻结"这个承诺目前不成立。

3. **固定资产有两处静默数据损坏点。** 一是残值率归一化（`normalizeSalvageRate`）漏了「拆分」和「盘盈调增」两个入口，配合 SCM/ACD 两个仍写百分数的写入方，会让残值被放大 100 倍、资产**静默停止折旧**（预览里连行都不出现，用户看不到任何报错）；二是原值减少没有「不得低于累计折旧 + 减值」下限，可直接把净值做成负数。

4. **历轮 P2 残留基本未动。** 总账第二轮报告 §二 P2、固定资产报告的 P2 清单，除少数顺带修的，绝大部分仍是原样。它们在正常流程下不致命，但正是 P0/P1 的"温床"（例如"凭证删除无期间闸"使已结账期间的凭证可被静默抹掉）。

**必须强调的口径**：本报告所有条目均基于静态代码走查并经人工复核（逐条给出 `文件:行号`）。其中 P0-3（残值率）与 P1-2（币别脱节）在当前开发库 `data/finance-0523.db` 中**尚无数据触发**（库内 `salvage_rate` 全部 ≤ 1、`cashier_journal` 只有 RMB/USD），属"路径确定但尚未显形"的潜伏缺陷——一旦发生 ACD 重导入或启用 SCM 收付款，即刻显形。

## 二、P0 —— 正确性 / 数据安全致命（4 项）

### P0-1　总账侧可完全绕过出纳结账：已结账月份的凭证仍可反记账 / 修改 / 反审核 / 冲红

**证据（"零引用"即证据）**

```
server/src/services/cashierPeriodClosing.ts:59 / :68      ← 出纳闸唯一实现
server/src/routes/cashierJournal.ts:30                     ← 全仓唯一 import 方
```

全仓 `grep -rn "cashierPeriodClosing" server/src` 只有 `migrationList.ts`（迁移注册）与 `cashierJournal.ts:30`（唯一调用方）。`routes/voucher.ts`、`routes/voucherAudit.ts`、`routes/voucherPosting.ts`、`routes/voucherBatch.ts`、`services/voucherEntry.ts` **从未引用它**。

各端点实际守卫：

| 操作 | 端点 | 现有守卫 | 是否含出纳闸 |
|---|---|---|---|
| 反记账 | `POST /vouchers/:id/unpost`（`voucherPosting.ts:283-295`） | 仅 `period_closing` | ❌ |
| 修改 | `PUT /vouchers/:id`（`voucher.ts:1325-1352`） | `period_closing` + cashier 仅"现金分录签名不变"（`:1274-1310`） | ❌（对方科目、日期可任意改） |
| 反审核 | `POST /vouchers/:id/unaudit`（`voucherAudit.ts:230`） | 仅 `validateVoucherForUnAudit`（`voucherEntry.ts:1415-1426`，只判 posted） | ❌ |
| 批量反审核 | `POST /vouchers/batch-unaudit`（`voucherAudit.ts:195`） | 同上 | ❌ |
| 冲红 | `POST /vouchers/:id/reverse`（`voucher.ts:858-1062`） | 只判红字凭证**目标**期间（`:912-920`） | ❌ |
| 删除 | `DELETE /vouchers/:id`（`voucher.ts:1744-1764`） | `getVoucherUndeletableReason`（`voucherDelete.ts:22`）**拦住了** | ✅ |

**触发场景（当前 UI 即可复现）**

1. 出纳结账 2026-09（`POST /api/cashier/periods/2026/9/close`），总账 2026-09 **保持未结账**。
2. 出纳侧生成凭证 → 审核 → 记账（`source='cashier'`，posted）。
3. `POST /api/voucher/vouchers/:id/unpost` → **200 成功**（只查 `period_closing`），`account_balances` 中出纳已结账月的余额被回退。
4. `PUT /api/voucher/vouchers/:id` 改对方科目或 `voucher_date` → **200 成功**；成功后 `routes/voucher.ts:1532` 调用 `services/cashierQuery.ts:913 syncCashierCounterFromVoucher`，把 `counter_account` 与 `voucher_year/voucher_month` **回写进已结账月份的 `cashier_journal`**。
5. `POST /api/voucher/vouchers/:id/reverse` → **200 成功**，在出纳已结账月生成红字草稿，而日记账仍指向原凭证。

**影响**：`cashierPeriodClosing.ts:6-10` 明文承诺"已结账月份的出纳日记账不再允许增删改 / 生成或删除凭证"，该承诺被总账侧整体破坏。出纳/总账月度数据脱钩，且出纳侧无任何操作痕迹（不产生出纳审计日志）。

**解决方案**

在 `services/voucherDelete.ts` 已具雏形的"统一凭证可变性守卫"基础上，扩展为一个共用函数，并在总账侧所有会改写现金/银行科目余额的写路径前置调用：

```ts
// services/voucherMutationGuard.ts（新建）
import { assertCashierPeriodOpen } from './cashierPeriodClosing.js'

/** 凭证可变性统一守卫：期间闸（总账 + 出纳）+ 来源守卫 */
export function assertVoucherMutable(params: {
  db: Database; accountSetId: string; voucher: DeletableVoucherLike
  operation: 'update' | 'unaudit' | 'unpost' | 'reverse' | 'delete'
}): string | null {
  const { db, accountSetId, voucher } = params
  // 1) 来源守卫（保留现有语义）
  if (voucher.source === 'cashier' && params.operation !== 'update') {
    // 删除/反审核/反记账/冲红一律拒绝，出纳凭证只能从出纳模块回收
    return '出纳生成的凭证不能在此操作，请到出纳模块处理'
  }
  // 2) 出纳期间闸：仅对现金/银行相关凭证生效
  if (isCashVoucher(db, voucher.id)) {
    try { assertCashierPeriodOpen(db, accountSetId, voucher.voucher_date) }
    catch (e: any) { return e.message }
  }
  return null
}
```

接入点（每条 3~5 行）：`voucherPosting.ts:283`、`voucherAudit.ts:230` 与 `:195`、`voucher.ts:1266`、`:858`、`voucherBatch.ts`。

> 备选（更省事但语义更粗）：只要 `period_closing` 与 `cashier_period_closing` 任一声明该期间已结账，就禁止上述所有写操作。适合作为第一步快速止血。

### P0-2　出纳侧不认总账期间闸：可向总账已结账 / 已年结期间生成新凭证

**证据**

```
server/src/services/cashierQuery.ts   ← grep "period_closing" 无任何命中
server/src/routes/cashierJournal.ts   ← 只有 assertCashierPeriodOpen（出纳自己的闸）
```

落库点在 `services/cashierQuery.ts:532 generateCashierVoucher`，其 `:599-600` 直接 `INSERT INTO vouchers`，全函数无任何总账期间校验。

**触发场景**

1. 账套 A：总账 2026-09 结账（`period_closing` 2026/9 = 'closed'），出纳 2026-09 未结账。
2. `POST /api/cashier/journal` `{account_code:'1001', biz_date:'2026-09-15', debit:1000, counter_account:'6001'}` → **200 成功**。
3. `POST /api/cashier/generate-voucher` → **200 成功**，已结账期间出现一张新凭证（`status='draft'`）。
4. 该凭证**永远无法记账**（`voucherPosting.ts:290` 拦"结账期间不能记账"），日记账 `voucher_no` 指向一张僵尸凭证。

**年结变体（更严重）**：上一年 2025 已年结（`yearClosing.ts:581-630` 已把余额写入 2026 期初）。只要出纳 2025 未结账，即可继续向 2025 补录流水并生成凭证——年结已固化的下年期初不包含这些凭证，**跨年勾稽永久断裂**。

**解决方案**

```ts
// services/cashierQuery.ts generateCashierVoucher 入口
assertGlPeriodOpen(db, accountSetId, year, period)   // 复用总账的 period_closing 判定
```

建议在 `services/voucherEntry.ts` 抽出 `assertGlPeriodOpen(db, accountSetId, year, period)` 并同时用于：
- `services/cashierQuery.ts:532 generateCashierVoucher`
- `routes/cashierJournal.ts:281-317`（日记账新增）
- `routes/cashierJournal.ts:407-450`（日记账导入）
- `routes/scmDoc.ts:3771-3783`（供应链单据生成凭证，见 P1-16）

### P0-3　残值率归一化漏网 + 两个写入方仍写百分数 → 残值放大 100 倍 → 资产静默停止折旧

**证据一：`normalizeSalvageRate` 的漏网点**

已接入（4 处）：`routes/fixedAsset.ts:477`（POST 新卡片）、`assetChange.ts:334`（原值变动）、`assetChange.ts:678`（折旧要素调整）、`assetCard.ts:142`（卡片 PUT）。

**未接入（2 处）**：

```ts

const salvageRate = Number(asset.salvage_rate || 0)      // ← 无 normalizeSalvageRate
...
round2(remainOriginal * salvageRate),                    // :760  父卡残值
...
    salvageRate,                                          // :830  子卡沿用脏率
    round2(childOriginal * salvageRate),                  // :831
```

```ts
// server/src/services/assetInventory.ts:387  —— 盘盈调增
const newSalvage = Math.round(newOriginal * Number(it.salvage_rate || 0) * 100) / 100
```

**证据二：仍写百分数的写入方**

```ts
// server/src/routes/scmDoc.ts:1835 —— 采购入库生成资产卡片
originalValue, 5, Math.round(originalValue * 0.05 * 100) / 100,
//             ↑ salvage_rate = 5（=500%），而 salvage_value = 5%（自相矛盾）
```

`server/src/scripts/importAcdCashierAsset.ts:307` `czl: num(row[7])` 同样把 ACD 的百分数原样入库。

> 迁移 `20260915_fix_salvage_rate_unit` 是**一次性**的——跑完之后新导入/新建的百分数卡片不会再被修正。

**触发场景（手工算账）**

设卡片：原值 10000、`salvage_rate = 5`、`salvage_value = 500`（SCM/ACD 建的卡，残值金额是对的，只有率是脏的）、使用 60 月。

- 拆分出子卡 3000 →
  - 父卡 `salvage_value = 7000 × 5 = 35000`
  - 子卡 `salvage_value = 3000 × 5 = 15000`，且子卡 `salvage_rate` 也写成 5，污染永久化
- 下一期计提，走 rebased 分支（`split` 已在 rebased 集合内，`fixedAssetDepreciation.ts:156-163`）：
  `remainingDepreciable = 7000 − 35000 = −28000 ≤ 0` → `return 0`（`:77-78`）
  → 父/子卡**永久静默停提，且预览里连行都不出现**（预览 SQL 过滤条件不含残值校验），用户看不到任何报错。
- 报表侧残值虚增 5 倍，净值/残值口径全废。

盘盈同理：原值 10000、qty 1、实盘 2 → `newOriginal = 20000` → `newSalvage = 20000 × 5 = 100000 > 原值` → 折旧同样归零。

**现场核对**：`data/finance-0523.db` 当前 262 张卡片 `salvage_rate` 全部 ≤ 1（迁移 123 已清理），**尚无数据触发**。但只要有新的 ACD 导入或 SCM 采购资产生成，即刻显形。

**解决方案**

1. **短平快**：`assetChange.ts:749` 与 `assetInventory.ts:387` 改为先 `normalizeSalvageRate()` 再计算并回写；`scmDoc.ts:1835` 改为 `0.05`；`importAcdCashierAsset.ts:307` 改为 `num(row[7]) / 100`。
2. **治本**：把归一化下沉到"任何写 `fixed_asset.salvage_rate` 的路径"。建议在 DB 层加兜底（SQLite 可用触发器）：
   ```sql
   CREATE TRIGGER trg_fa_salvage_rate_guard
   BEFORE INSERT ON fixed_asset
   FOR EACH ROW WHEN NEW.salvage_rate > 1
   BEGIN SELECT RAISE(ABORT, 'salvage_rate 必须为 0~1 的小数'); END;
   ```
   （`UPDATE` 同理建一条。）这样任何漏网的写入路径都会立刻失败，而不是静默产生错账。
3. `normalizeSalvageRate` 目前对 `>= 1` 放行（见 P2-14），建议一并收紧为 `>= 1` 拒绝。

### P0-4　盘点盘亏重复核销：已处置 / 已核销的卡片仍会再生成一张"整卡核销"凭证

**证据**

```ts
// server/src/services/assetInventory.ts:432-438 —— 盘亏明细查询
WHERE i.inventory_id = ? AND i.actual_status = 'deficit'      // ← 无 scrap_date / 已核销过滤
```
```ts
// server/src/services/assetInventory.ts:511-517 —— 凭证分录
push(item, deficitAccCode, 'debit',  item.book_net_value,     label)
push(item, deprAccCode,    'debit',  item.book_accum_depr,    `盘亏冲销折旧：...`)
push(item, item.asset_account || '1601', 'credit', item.book_original_value, label)
```
```ts
// server/src/services/assetInventory.ts:332-333 —— 卡片侧却会跳过
for (const it of items) {
  if (it.scrap_date) continue    // 已处置的不重复处理   ← 卡片不重复，凭证照样重复
```

**触发场景（手工算账）**

卡片 A：原值 10000 / 累折 4000 / 净值 6000。

1. 先对 A 办理处置（凭证：借 1602 4000 + 借 1606 6000 / 贷 1601 10000）；
2. 再完成一张"含 A 且 A 被标记为盘亏"的盘点 →
   `generateInventoryVoucher` 用**盘点创建时的快照**再次入账：借 6901 6000 + 借 1602 4000 / 贷 **1601 10000**。

→ `1601` 贷方累计 20000，而该资产账面仅 10000：**固定资产科目余额被冲成负数**，吃掉其他资产的余额；`1602` 多借 4000。卡片因 `scrap_date` 已存在被跳过，**用户从卡片上完全看不出重复**。

同一路径也覆盖"重复盘点"：盘点 2 在盘点 1 **完成之前**创建（`createInventory` 只按创建时点过滤 `scrap_date IS NULL`），两轮都能把同一卡片标为盘亏并各生成一张核销凭证。

**解决方案**

```sql
-- deficitItems / surplusItems 查询补一句
LEFT JOIN fixed_asset fa ON ...
WHERE i.inventory_id = ? AND i.actual_status = 'deficit'
  AND fa.scrap_date IS NULL                    -- 已处置的不再核销
  AND fa.status_code <> '04'                   -- 已报废的不再核销
```

并在 `completeInventory` 前增加一致性校验：卡片当前值 == 清单快照值，不一致则提示"资产在盘点期间发生变动，请重新盘点"，避免用陈旧快照入账。

#### P1-1　SCM 收付款单审核 / 反审核直接增删出纳日记账，完全绕过出纳结账闸

#### P1-3　`POST /cashier/reset` 权限错挂、清空结账记录、不清理出纳凭证


权限规则（`cashierJournal.ts:75-93`）中 `/cashier/reset` 不匹配前面任何一条，落入最后一条 catch-all `{ re: /^\/cashier\//, perm: 'cashier:journal' }`（`:92`）。而菜单权限是另一个码：

```
client/src/config/navigation.ts:485   permission: 'cashier:initbal'
```

**三重问题**：① 只有 `cashier:journal`（单据录入岗位）的用户可调该接口清空账套全部出纳数据，而菜单显示的 `cashier:initbal` 用户反而被 403；② 无结账闸且直接删除 `cashier_period_closing`，等于用"初始化"绕过"反结账"流程，**审计冻结月份的数据可被一次抹掉**；③ 只删表数据，不清 `source='cashier'` 的凭证 → 凭证与出纳数据永久不一致，而这些凭证在总账侧被判定为"不可直接删除"（`voucherDelete.ts:22`），只能靠出纳"批量删除凭证"按日期范围回收。

#### P1-4　删除 / 修改"已对账"日记账不校验对账状态 → `bank_statement.matched` 成孤儿，调节表永久不平

```ts
// server/src/routes/cashierJournal.ts:365-403  DELETE /cashier/journal/:id
//   只查了 voucher_no / posted，全程未读 reconciled，也未清理 bank_statement
// server/src/routes/cashierJournal.ts:319-363  PUT /cashier/journal/:id
//   允许改 debit/credit，同样不校验 reconciled
```

对账数据源：`cashierQuery.ts:473-503`（`reconciled=0` 才进"企业已记银行未记"，`matched=0` 才进"银行已记企业未记"）。

**触发**：勾对一条 100 元日记账与对账单 → 在日记账页删除该行 → 打开"余额调节表"：该 100 元两侧均不出现（日记账侧因行被删、对账单侧因 `matched=1` 被排除），**差额恒等于 100**；且用户无法自行修复——对账单因 `matched=1` 被 `:492` 禁止删除。

改金额更隐蔽：日记账金额变了、对账单还是旧金额，两表不再对应。

**解决方案**：删除/修改入口先判断 `reconciled=1` → 提示"请先撤销勾对"；或在同一事务内反写 `bank_statement SET matched=0, match_batch=NULL`。

#### P1-5　自动勾对全批共用一个 `match_batch`，撤销一条会把同批次其他对账单全部置为未匹配


#### P1-7　日期解析失败静默放行：非法 / 异形日期可完全绕过结账闸口并入库

```ts
// server/src/services/cashierPeriodClosing.ts:52-56
export function parseBizDate(bizDate) {
  const m = /^(\d{4})-(\d{2})/.exec(String(bizDate || ''))
  if (!m) return null
  ...
}
// :59-65
export function assertCashierPeriodOpen(db, accountSetId, bizDate) {
  const ym = parseBizDate(bizDate)
  if (!ym) return          // ← 解析失败直接放行（fail-open）
```

后端新增/导入无日期合法性校验（`cashierJournal.ts:290-291`、`:430` 只判非空）；对账单导入把 `/`、`.` 换成 `-` 但不补零（`cashierImport.ts:138-145`）；前端导入正则不匹配时**原样返回**（`client/src/views/cashier/Journal.vue:1549-1558`）。

**触发**：`2026/01/15`、`2026-1-5`、`2026-13-01`（月 13）都能通过 `!biz_date` 校验并落库，其 `parseBizDate` 全部返回 `null` → **闸口不生效**。

更隐蔽的两种：
- `substr(biz_date,6,2)`（`cashierPeriodClosing.ts:143`）对 `2026/01/15` 恰好取到 `'01'` → **结账页显示该月有 N 笔，但闸口从不拦这一笔**；
- `2026-1-5` 在字符串比较下（`biz_date >= '2026-01-01'`）排序异常，会在所有日期区间报表中**静默丢失**；
- Excel 数字型日期（未套日期格式）会以 `'45876'` 落库，该行在流水账中永远排在最前，逐行余额全错。

**解决方案**：写入口统一做严格规范化 + 校验（`^\d{4}-\d{2}-\d{2}$` 且真实存在、月 01-12），失败返回 400；`assertCashierPeriodOpen` 用于写路径时必须 **fail-closed**（解析失败即抛错）；前端 `normExcelDate` 补数字型 Excel 序列号处理。

#### P1-8　结账 `year` 未校验整数：一次畸形请求即可永久锁死出纳结账功能

```ts

// server/src/services/cashierPeriodClosing.ts:199
if (!year || !month || month < 1 || month > 12) throw new Error('年月不合法')   // ← 只校验 month
```
```ts

if (latest && latest.year * 100 + latest.month > key) {
  return `${latest.year}年${latest.month}月已结账，不能回头结更早的月份`   // ← 锁死点
```

**触发**：`POST /api/cashier/periods/2026.5/9/close`（body 空）→ `Number('2026.5') = 2026.5` 原样写入（SQLite 允许 REAL 进 INTEGER 列）→ **200**。
此后：

- `listCashierPeriodStatus` 按 `year=?`（`:133`）、`isCashierPeriodClosed` 按 `year=?`（`:43`）都查不到该行 → 前端年下拉只列整数年份，**无法选出该行来反结账**；

**解决方案**：`/cashier/periods/:year/:month/*` 路由用 `^\d{4}$` / `^\d{1,2}$` 约束并在 handler 内 `Number.isInteger` 双校验；`closeCashierPeriod` 增加 `Number.isInteger(year) && year >= 2000 && year <= 2100`；`getLatestClosedCashierPeriod` 增加 `year BETWEEN 2000 AND 2100` 兜底。

#### P1-9　可结未来月份，且结掉 12 月后无法回头结 1–11 月

`closeCashierPeriod` 只校验 `month in 1..12`（`cashierPeriodClosing.ts:199`），无"不得晚于当前会计期间"的判断；顺序约束只在"更早的有数据月份未结"方向生效（`:96-118`）。

**触发**：2026-09 时把 2026-12 结掉 → 1–11 月全部落进 `latest(2026-12) > key` 分支被拒 → 必须先反结 12 月。而 12 月尚未发生业务，结账语义本身无意义；同时 12 月被结后也无法再向 12 月录入日记账。

**解决方案**：结账时校验 `(year, month) <= 当前会计期间`（参考总账 `period_closing` 的做法）；前端 `PeriodClose.vue` 的年份/月份候选项按当前期间裁剪。

#### P1-11　凭证重排号 / 插入凭证后，出纳日记账的 `voucher_no` 脱钩

出纳页面删除凭证后会主动提示重排号（`client/src/views/cashier/Journal.vue:1399-1400`），但重排号只改 `vouchers` 表（`routes/voucher.ts:288-301`），**未同步 `cashier_journal.voucher_year/month/type/no`**。而出纳日记账正是用这四个冗余字段作为凭证关联的**唯一凭据**（`cashierJournal.ts:570-575`、`:380-383`、`cashierQuery.ts:937-946`）。

**解决方案**：给 `cashier_journal` 增加 `voucher_id` 列作为真正的外键，号只作展示；重排号/插号时按旧号定位出纳行并同步刷新（复用 `syncCashierCounterFromVoucher` 的 `CAST` 比较写法）。

#### P1-17　原值减少无「不得低于累计折旧 + 减值」下限 → 净值负数 → 折旧静默停止 + 处置凭证必然借贷不平

```ts

if (newOriginal < 0) throw new Error('变动后原值不能为负数')   // ← 唯一校验，只挡负数

```

全模块（含 `routes/fixedAsset.ts:764-819` 与前端 `AssetChange.vue:623-628`）均无 `newOriginal >= accum_depr + impairment` 校验。

**触发场景（手工算账）**：原值 1000、累折 800、残值率 0.05、使用 24 月已提 8 月。做「原值减少 500」：

- `newOriginal = 500`，`newSalvage = 25`，**`net_value = 500 − 800 − 0 = −300`**

- 前端处置弹窗预估损益 = `收入 − 费用 − (−300)` = 收入 **+300 虚增收益**（`client/src/views/asset/AssetList.vue:703-707` `disposePreviewGainLoss`）

**解决方案**：`applyValueChange` 增加

```ts

if (newOriginal < floor) {
  throw new Error(`变动后原值 ${newOriginal} 不能低于累计折旧+减值 ${floor}，请先办理减值/报废`)
}

```

#### P1-18　已提满的资产发生「原值增加 / 改良但不延长月数」后**永久不再计提**

```ts
// server/src/services/fixedAssetDepreciation.ts:72
```

**触发场景（手工算账）**：原值 100000、残值 5000、60 月已提满（累折 95000、净值 5000）。做「原值增加 20000」：

## 五、解决方案：收口设计（推荐实施顺序）

本轮 25 个 P0/P1 中有 **11 个是"守卫漏挂"** 这一类问题。逐个补守卫会不断复发，因此建议先做**收口**，再补业务规则。

### 第 0 步（止血，1~2 天）

1. **统一凭证可变性守卫**：新建 `server/src/services/voucherMutationGuard.ts`，导出 `assertVoucherMutable({ db, accountSetId, voucher, operation })`，内部同时判定：来源守卫 + 总账期间闸 + 出纳期间闸。接入 `voucherPosting.ts`、`voucherAudit.ts`(×2)、`voucher.ts`(×3)、`voucherBatch.ts`。
   → 一次性消掉 P0-1、P1-12、P1-13、P1-14、P1-15。
2. **统一期间写入闸**：在 `voucherEntry.ts` 抽出 `assertGlPeriodOpen(db, accountSetId, year, period)`，接入出纳生成凭证与 SCM 生成凭证。
   → 消掉 P0-2、P1-16。
3. **出纳闸 fail-closed + 日期严格校验**：`assertCashierPeriodOpen` 解析失败即抛错；所有写入口统一 `normalizeBizDate()`（严格 `^\d{4}-\d{2}-\d{2}$` + 真实性校验）。
   → 消掉 P1-7；同时让 P1-6 的漏挂入口"即使忘了接闸也会因为日期不规范被拦"（部分兜底）。
4. **结账参数校验**：`Number.isInteger(year)` + 期间上限；`getLatestClosedCashierPeriod` 加年份范围兜底。
   → 消掉 P1-8、P1-9。

### 第 1 步（数据完整性，2~3 天）

   → 消掉 P1-4、P1-5。
