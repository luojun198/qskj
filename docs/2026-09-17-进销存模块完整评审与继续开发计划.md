### 二、本轮新发现：P0 四项、P1 十三项、P2 十八项

问题集中在三类，**都不是核心引擎算错，而是"接线漏了"和"占位功能被当成可用功能"**：

1. **两条链路"读侧写好了、写侧没接"**（P0-1、P0-2）。这是本轮最典型也最危险的一类：
   - 发票反审核的分支写反了，`reverseInvoice` 成了**永不执行的死代码**，下推发票反审核后来源单的暂估额**永久停在发票金额**；
   - 退货单（PR/SR）审核**不写往来台账**，但 `AR_DOC_TYPES`/`AP_DOC_TYPES`/`enrichStatementRows` 的 `isAdjustment` 分支**早就为 PR/SR 准备好了读逻辑**——读侧在等一个永远不存在的数据。
2. **"字段有 UI、后端有列、运算不读"的占位功能**（这是制定开发计划的核心依据）。BOM 的版本/生效期、替代料组、副产品/联产品行、工艺路线的工序委外开关，这四项**全部是写了不读**。用户以为配了会生效，实际配了等于没配——这比明确标注"未实现"更危险。
3. **序列号台账在非"单向出入库"单据上失守**（P0-3、P0-4）。调拨反审核会**物理删除**序列号档案（原始入库追溯永久丢失、且单据再也无法审核）；组装/拆卸完全不维护批次与序列号，导致已被组装消耗的序列号仍是"在库"状态、**可被再次销售出库**。

### 三、关于"继续开发"的判断

进销存模块目前的状态是：**销售/采购/库存/生产/委外的"主流程"已可交付，但"边缘但会真出账"的路径（退货、折扣、组装拆卸、序列号、发票下推）有明确的账实不符缺口；而"配置类功能"（BOM 版本/替代料/副产品、工序委外、计价方式、质检深度）大面积是占位。**

因此本计划的策略是 **"先堵账实不符，再决定功能去留，最后补真正的功能"**：
- 阶段 A（1 周）：修 P0，让已配置的功能不再产生错账；
- 阶段 B（1.5–2 周）：修 P1，让退货/折扣/发票/工单/账龄这条链闭环；
- 阶段 C（关键决策 + 3–4 周）：**先对 7 项占位功能做"实现 or 撤下 UI"的抉择**（这是本计划最重要的部分，见 §六 阶段 C），再实施；
- 阶段 D（1–2 周）：口径收敛、前端接线、性能；
- 阶段 E（贯穿）：测试与数据基线补齐。

> **必须强调**：开发库当前 **SCM 业务数据为空**，意味着本轮所有结论都是静态走查结论，无法用真实数据交叉验证。阶段 A 之前建议先建一套"进销存回归账套"（见 §六 阶段 0），否则修完也验证不了。

## 二、P0 —— 数据静默损坏 / 不可恢复（4 项）

### P0-1　发票反审核走错分支：`reverseInvoice` 是永不执行的死代码，来源单暂估额永久不还原

**证据**

```ts
// server/src/routes/scmDoc.ts:1761-1768
if (isPaymentDoc || doc.doc_type === 'RP' || doc.doc_type === 'RS') {
  reversePayment(db, aid, doc)        // ← RP/RS 落到这里
} else {
  ...
  if (doc.doc_type === 'RP' || doc.doc_type === 'RS') reverseInvoice(db, aid, doc)   // ← 永不可达
```

`reversePayment`（`scmArAp.ts:245-272`）只删 `WHERE doc_type=? AND doc_no=?`（即**发票自己号**的台账行）。但下推发票在 `applyInvoice` 的 `adjust` 模式下**从未以发票号建过台账**，只 `UPDATE` 了来源单那一条（`scmArAp.ts:135-137`）→ `reversePayment` 对它完全是个 no-op。
全仓 `reverseInvoice` 引用点只有 2 处：`scmDoc.ts:12`（import）与 `:1768`（死分支）。

**触发场景**

1. PI 采购入库 1000 审核 → 台账挂 1000，凭证按 1000 出账。
2. 由该 PI 下推 RP 采购发票 800 审核 → `applyInvoice` 把**来源台账改写为 800**（备注留下 `[发票 RP-xxx]`）。
3. 反审核 RP → `reversePayment` 删 0 行；来源台账**仍是 800**。
4. 结果：单据行金额合计 1000、总账暂估 1000、凭证 1000，而往来台账/账龄/对账单 = 800。**差额 200 永久静默存在**。此时即使删除发票或改金额重审，来源暂估也不会回到 1000。

**解决方案**

把 `RP/RS` 从外层 `if` 摘出，改为按"是否有来源单据"分流：

```ts
if (isPaymentDoc) {
  reversePayment(db, aid, doc)
} else if (doc.doc_type === 'RP' || doc.doc_type === 'RS') {
  reverseInvoice(db, aid, doc)      // 内部已按 source_doc_id 区分「还原来源暂估 / 删自己台账」
} else {
  if (doc.doc_type === 'SO' || doc.doc_type === 'PI' || doc.doc_type === 'WI') reversePayment(db, aid, doc)
}
```

并补一条**走 `/scm/docs/:id/unaudit` 路由**（而不是直调 service）的回归用例——现有 `scmInventoryArap.test.ts:250-275` 直调 `reverseInvoice`，所以测试全绿却掩盖了线上不可达。

### P0-2　退货单（PR/SR）审核不写往来台账：读侧早已写好、写侧从未接上

**证据**

审核挂账分支只覆盖 4 类：

```ts
// server/src/routes/scmDoc.ts:1692-1701
if (doc.doc_type === 'SO') { applyReceivableFromShipment(db, aid, doc, lines) }
else if (doc.doc_type === 'PI') { applyPayableFromReceipt(db, aid, doc, lines) }
else if (doc.doc_type === 'RP' || doc.doc_type === 'RS') { applyInvoice(...) }
// ← 没有 SR / PR
```

而读侧**已经为 PR/SR 准备好了分支**：

```ts
// server/src/services/scmArAp.ts:275-276
const AR_DOC_TYPES = ['SO', 'SR', 'RS', 'RCV']
const AP_DOC_TYPES = ['PI', 'PR', 'RP', 'PAY', 'WI']
// server/src/services/scmArAp.ts:308-312（对账单富化）
const isAdjustment = ['PR', 'SR'].includes(row.doc_type)
... adjustment_amount: isAdjustment || (row.direction === 'out' && !isSettlement) ? Number(row.amount) || 0 : 0
```

全仓 `INSERT INTO scm_ar_ap_log` 仅 5 处（`scmArAp.ts:61/184/208/223/235`），均不涉及 PR/SR。而总账侧退货**确实冲减**应收应付（`scmDoc.ts:3672/3679`）。

**触发场景（手工算账，13% 税率）**

```
06-01 销售发货 SO   含税 11300（10000 + 1300） → 台账 in 11300
07-05 收款单   RCV  5000                        → 台账 out 5000，核销 5000
07-20 销售退货 SR   含税  2260（2000 + 260）   → 台账：无！凭证：贷应收 2260

期望应收 = 11300 − 5000 − 2260 = 4040
往来余额 = 11300 − 5000        = 6300   ← 差 2260（整笔退货价税合计）
总账 1122 = 11300 − 5000 − 2260 = 4040
```

影响面：往来余额、账龄、到期提醒、信用占用、对账单**全部虚增**；该 SR 连对账单行都不会出现；"未核销应收"虚高导致**信用额度误判**（客户已清账仍显示欠款）。若整月退货 100 万，1122 明细账就比往来说明多 100 万。

**解决方案**

在审核分支补 PR/SR，按价税合计写一条**冲减台账**（`direction='out'`，或 `in` + 负金额并在 `applyInvoice`/`enrichStatementRows` 统一符号口径），反审核对应删除。需同步 `getArApAging` 的分桶、`getPartnerOpenAr`、`getPartnerBalanceSummary` 的 AR/AP 归类。

2. TR 调拨 SN-001 从 A 仓到 B 仓审核 → `serialIn` 把 `in_doc_no` **覆盖为 TR-002**。
3. 反审核 TR-002 → 按 `rowid DESC` 先处理目标仓的 `in` 流水 → 判定"本单即当前入库来源" → **整条 `scm_serial` 行被 DELETE**；随后原仓 `out` 流水的回退因查不到行而被 `continue` 跳过。
4. 最终 `DELETE FROM scm_serial_move WHERE doc_id=?` 把该单全部追溯流水一并删除。

三重后果：
- ① SN-001 的**原始入库单据追溯信息（PI-001）与全部移动历史不可恢复地消失**（无软删除、无留痕）；
- ② A 仓库存数量已由 `reverseDocMoves` 正确回滚，但序列号台账里已无该 SN → **两个台账永久不勾稽**；
- ③ 重新审核 TR-002 → `serialOut` 抛"序列号 SN-001 不在库，无法出库" → **单据再也无法审核**，只能人工重建档案。

**解决方案**

在 `scm_serial_move` 上记录回退所需的现场（`prev_status / prev_doc_no / prev_warehouse`），反审核时据此**还原**而不是"按 `in_doc_no` 相等即删除"；或给 `scm_serial` 增加 `created_doc_no`（建档单据，永不被入库覆盖），只有建档流水才允许删除。

#### P1-2　手工录入的销售退货（SR）以"售价"作为入库成本，并据此冲回主营业务成本
