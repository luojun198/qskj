## 〇、对报告的核实与修正

所有 P0/P1 论断均已对照代码确认属实（文件行号见下表）。两处补充：

1. **P0-1 真正的触发条件是「日期区间窄」而非「缺参数」**。`buildLedgerGeneralQuery` 缺参默认当月，SQLite 对窄区间改走 `idx_vouchers_date → voucher_id 反查分录` 计划，954 个科目逐个走相关子查询。用户在页面上选一个月区间同样可能命中。因此 SQL 改写是主修复，参数收口只是兜底。
2. **数量余额表 `buildQuantityBalanceQuery`、外币余额表 `buildForeignBalanceQuery` 与 general 是同一套写法（相关子查询 + 缺省当月）**，需一并改写，否则只是把雷从一张表挪到另一张。

| 问题 | 代码位置 |
|---|---|
| general 路由不读 year | `server/src/routes/ledger.ts:155-189` |
| 缺省当月 + 8 个相关子查询 | `server/src/services/ledgerQuery.ts:195-200, 305-330`（数量表 :1806、外币表 :2021 同款） |
| 明细账全量拉取喂 el-table | `client/src/views/ledger/Detail.vue:586-616`（FIX-158 有意全量） |

## 一、阶段划分

### 阶段 1（P0，立即）：余额表 SQL 改 CTE 聚合 + 参数收口 ✅ 已完成（FIX-250，2026-09-19）

> 实测：缺参 209s → 0.47s，全年 1.85s → 0.46s，单月 0.36s，总分类账 2.3s → 0.48s。CTE 采用凭证驱动（CROSS JOIN），voucher_entries 覆盖索引实测无收益未加。

**目标**：任意日期区间、任意调用方，`/ledger/general` 十万级 ≤2s，且不阻塞其他请求。

1. **`buildLedgerGeneralQuery` 改写**（`ledgerQuery.ts`）
   - 先用 `EXPLAIN QUERY PLAN` 复现「当月区间」慢计划，记录基线（脚本放 `scratch/`）。
   - 把 8 个相关子查询合并为一个 CTE：一次扫描 `voucher_entries JOIN vouchers`（按 `account_set_id + 状态 + 日期 ∈ [min(startBaseYearStart, …), endDate]`），用 `SUM(CASE WHEN v.voucher_date < ? THEN … END)` 分桶算出 init / current / year 各列，再 `LEFT JOIN accounts`。写法参考 `buildGeneralLedgerQuery`（`/ledger/general-ledger` 已在用，实测 1.6s）。
   - 账前（pre-book）表达式 `buildAccountOpeningBalanceExpr / buildAccountPreBookSideExpr` 同样并入 CTE 或保持独立小子查询（它们不扫分录表，代价低，可暂不动）。
   - **数量余额表、外币余额表**用同一 CTE 骨架改写（金额列换 `quantity` / `foreign_amount`）。
2. **参数收口**（`routes/ledger.ts` `/general`、`/quantity-balance`、`/foreign-balance`）
   - 缺 `start_date/end_date` 时：若有 `year` → 该年 1/1~12/31；都没有 → 当年全年；并 `console.warn` 一条含调用路径的日志。
   - 不再默认「当月」（三个 build 函数的 `defaultStartDate/EndDate` 同步改为当年全年）。
3. **索引**（新迁移 141 `20260919_ledger_balance_indexes.ts`）
   - 确认 `idx_voucher_entries_account_date` 是否仍存在（迁移里出现过 DROP）；若无则建 `voucher_entries(account_set_id, account_id, voucher_date)`——需先看 `voucher_entries` 是否冗余存了日期，没有则建 `vouchers(account_set_id, status, voucher_date)` 覆盖索引。
   - 迁移末尾 `ANALYZE`。
4. **验证**
   - 单测：`ledgerQuery.test.ts` 现有用例全过 + 新增「窄区间 / 跨年 / 账前」三组金额一致性断言（改写前后结果逐行相等）。
   - 压测：`node scratch/glStressTest.mjs --stages=AB`，`?year=2026`、`?start=09-01&end=09-30`、全年三种口径均 ≤2s。

**工作量**：1 天。**风险**：CTE 改写涉及期初/本年累计口径，必须用改写前 SQL 做对照回归，不能只看不报错。

### 阶段 2（P0，本周）：明细账 / 序时账页面渲染 ✅ 已完成（FIX-251，2026-09-19）

> 实测 10 万行 mock：>300s 无响应 → 首屏 2.0s / 最长长任务 259ms / 堆 125MB。取备选方案「前端分页 200 行/页」：`el-table-v2` 不支持列宽拖拽记忆、`row-class-name` 小计样式与现有 compact 样式。序时账已是服务端分页（≤500）未改。

**目标**：单科目 10 万行明细账页面可交互，主线程长任务 <1s。

1. **`Detail.vue` 改虚拟滚动**：主表换 `el-table-v2`（复用 `VoucherAuditTable.vue` 的列适配写法），保留 `fetchAllPages` 全量拉取（数据链路已验证 3s/169MB 不是瓶颈），只改渲染层。这样 FIX-158「不截断」的语义不变，打印/导出路径无需动。
   - 若 `el-table-v2` 与现有 `useFillHeightTable` / 合并行 / 固定列样式冲突较大，退而求其次：主表保持 `el-table` 但**前端分页显示**（每页 500，底部翻页），全量数据仍在内存供导出。
2. **`Chronological.vue`（序时账）**：同样处理；它已是服务端分页，只需确认 pageSize 上限（≤500）与导出路径分离。
3. **兜底提示**：`fetchAllPages` 加 `maxRows`（默认 20 万）与 `onExceed` 回调；页面在 `total > 5 万` 时 `ElMessageBox.confirm` 提示「建议缩小范围或直接导出」。
4. **验证**：Playwright 复现报告 §四 用例（mock total=100,000），`PerformanceObserver(longtask)` 最长任务 <1s，DOM 行数 ≤ 视口两屏。

**工作量**：1.5 天。

### 阶段 3（P1，本周）：后端阻塞与全量拉取 ✅ 已完成（FIX-252 / FIX-253，2026-09-19）

> 实测：批量记账 3,000 张 52s → 4.3s，期间轻接口 P95 176ms / 明细账 98ms；出纳首页 601ms → 72ms、RSS 恒定；序时账预取 45s → 28s。额外发现：单张过账 89% 耗时在逐科目期初试算（923 次查询 → 1 次）。

1. **批量过账分片让出事件循环**（`batchOperationAsync.ts`）
   - 每 50 张：`await new Promise(r => setImmediate(r))`；`updateTask` 改为每 50 张或每 500ms 写一次，不再每张写。
   - 每 100 张包一个 `db.transaction`（减少 WAL fsync 次数，17ms/张 主要是 fsync）；单张失败在事务内 catch，记录错误不回滚整批（与现有逐张语义一致）。
   - `batchUnpostAsync` 同样处理。
   - 目标：3,000 张 ≤15s，且期间其他 API P95 <200ms（压测脚本加「批量记账期间并发查明细账」用例）。
2. **出纳日记账分页**（`cashierQuery.ts listJournal`、`routes/cashierJournal.ts`、`views/cashier/Journal.vue`）
   - 路由接收 `page/page_size`（默认 100，上限 1,000）。
   - 期初余额：`SUM(debit - credit) WHERE biz_date < 本页首行` 一条 SQL 算出，本页逐行累加；`total_debit/credit` 用一条聚合 SQL。
   - 前端 `Journal.vue` 已按 `data.list` 消费，补翻页组件；导出/打印路径走 `page_size=全量` 或服务端导出。
   - 目标：首页 <50ms，RSS 增量 <10MB。
3. **序时账导出预取 45s**（`utils/ledgerFetchAll.ts` + `routes/ledger.ts` 序时账）
   - 序时账路由支持 `skip_count=1`：非首页不再执行 `COUNT(*)`；`fetchAllPages` 第 2 页起传该参数。
   - 预期从 45s 降到 ~15s；根治见阶段 4。

**工作量**：1.5 天。

### 阶段 4（P1，下周）：导出改「参数模式」+ 导入分批 ✅ 已完成（FIX-254 / FIX-255，2026-09-19）

> 实测：spec 导出 10 万行 11.3s → 5.5s 且不阻塞；序时账参数模式 24 万行 15s、RSS 558MB、并发 P95 204ms；出纳导入 7.1s → 3.7s、对账单确认 4.0s → 1.0s、导入后 RSS 1.38GB → 460MB。额外发现：序时账 / 明细账导出原走浏览器端 ExcelJS；operationLog 把整份请求体落库是内存驻留主因。参数模式暂只落地序时账（明细账改服务端 spec 模式，余额表数据量小无需）。

1. **服务端参数模式导出**（`routes/export.ts`、`utils/exportStyledExcel.ts`）
   - `POST /export/styled-xlsx` 新增 `source: { endpoint, params }`：服务端自己调查询函数取数并构建 xlsx，前端不再拉全量。
   - 先落地序时账、明细账、余额表三张（占导出流量 90%）；其他页面维持现有 spec 模式。
   - ExcelJS 改 `stream.xlsx.WorkbookWriter` 流式写入，峰值 RSS 从 1.1GB 降到 <300MB。
   - 前端：`total > 5 万` 自动走参数模式，否则沿用现路径（避免一次性改所有页面）。
2. **导入分批事务**（出纳导入、银行对账单确认）
   - 服务端：每 5,000 行一个事务；处理完置空 rows 引用；`--expose-gc` 不用，靠分批降峰值。
   - 前端：>1 万行时按 1 万行分批 POST，复用 `TaskProgressDialog` 显示进度。
   - multer 上限 20MB → 50MB，超限时返回明确文案「请拆分文件（约 12 万行/份）」。
   - 目标：10 万行导入后 RSS ≤500MB 且 60s 内回落。

**工作量**：2 天。

## 三、不做 / 暂缓

- **不引入 worker_threads 跑 SQL**：better-sqlite3 同步阻塞是根本约束，但把慢查询搬到 worker 只是把 209s 藏起来，不解决计划劣化；阶段 1 把慢查询本身消灭更直接。若阶段 1 后仍有 >5s 的报表，再评估 worker 池。
- **不改 el-table 全站**：只动明细账/序时账两个十万级页面。
- **不动 FIX-158 的「全量不截断」语义**：改渲染层不改数据语义。

### 额外发现（报告未覆盖）
- 单张过账 89% 耗时在逐科目期初试算（923 次查询 → 1 次），单张记账同样受益
- 序时账 / 明细账「导出 Excel」原本在浏览器端生成，不是服务端
- `operationLog` 中间件把批量接口整份请求体写进 `operation_logs`，是导入后内存驻留主因
- 规划器统计陈旧（开发库小表统计）会让余额表 CTE 误选索引（0.45s → 1.5s）：批量导入 / 批量记账后现在会 `PRAGMA optimize`，服务每小时也会跑
- 阶段 1 草稿建过的 `idx_voucher_entries_voucher_account` 会把实时余额查询带偏（2ms → 515ms），已从开发库删除，迁移 142 正式版不含它
