# 销售订单合并出库——按订单数量 × 库存数量自动填写发货

## 问题诊断

URL `/scm/docs?doc_type=SOa` 多选订单「合并出库」的"自动填写发货数量"逻辑当前有缺陷：

- 「合并出库」按钮已存在（`client/src/views/scm/DocList.vue:44-45`）
- 后端 `POST /scm/docs/batch-availability`（`server/src/routes/scmDoc.ts:1909`）已正确算出每行 `ship_qty = min(订单剩余, 可用库存)`，可用库存已扣除其他未发货订单占用
- **缺陷**：前端 `buildSalesDispatchLines`（`client/src/utils/scmSalesDispatch.ts:14-16`）只取 `base_remaining ?? remain`（订单剩余量），**完全忽略了已算好的 `ship_qty`**
- 结果：库存不足时生成的 SO 草稿行数量超过库存，审核失败，用户需手动逐行改

## 用户已确认的产品决策

1. 数量策略：**按可用库存限制** — 发货 = min(订单剩余, 可用库存)
2. 交互：**新增一个库存对比预览全页面**（类似单订单 `StockDispatch.vue`），让用户确认 `ship_qty` 后再生成 SO 草稿

## 实现方案（遵循 AGENTS.md「复杂交互用全页面」原则）

### 1. 新增预览页面 `client/src/views/scm/MultiDispatch.vue`

仿照 `StockDispatch.vue` 的整体结构（顶部导航 + 提示条 + 表格 + 底部统计），但针对**多订单**：

- **顶部导航**：`返回 + 标题「合并出库 / 多订单库存对比」+ 客户名 + 币别 + 订单数量` 标签
- **提示条**：解释算法 `可用库存 = 现存量 − 其他未发货订单占用；本次发货默认 = min(订单剩余, 可用库存)，库存不足部分本次不发，可下次再发或进 MRP`
- **表格列**（基于 `ScmStockAvailLine`）：
  - `源单号 + 源单日期`（新增两列，标识每行属于哪张订单——多订单合并的关键差异）
  - `编号 / 名称 / 规格 / 单位 / 仓库`
  - `订单数量 / 已下推 / 订单剩余 / 可用库存`（只读展示）
  - **`本次发货`（`el-input-number`，默认 `ship_qty`，min=0，max=`overrun_remaining`）**
  - `缺口`（订单剩余 − 本次发货，标红提示本次未发完的部分）
- **底部统计**：可发合计、订单剩余合计、缺口合计
- **生成按钮**：`生成销售出库草稿（N 行）` → 调 `scmApi.createDoc({ doc_type: 'SO', source_doc_ids, partner_code, warehouse_code, lines })`，每行带 `source_line_id`，过滤掉 `ship_qty=0` 的行；成功后跳 `ScmDocEdit`
- **数据加载**：`onMounted` → `scmApi.getBatchDocAvailability(ids)` 解析 query `source_doc_ids`
- **复用样式**：直接复用 `StockDispatch.vue` 的 `.sd-*` 样式类（提取或本地复制）

### 3. 修改 `client/src/views/scm/DocList.vue` 的「合并出库」入口

将 `handlePush`（line 614-623）的多订单分支改为**先进预览页**：

```ts
function handlePush() {
  if (!actionState.value.push.enabled || !actionState.value.push.targetType) return
  const ids = selection.value.map(row => row.id!).filter(Boolean)
  // 销售订单合并出库：先进库存对比预览页，再生成 SO 草稿
  if (ids.length > 1 && actionState.value.push.targetType === 'SO') {
    router.push({ name: 'ScmDocBatchDispatch', query: { source_doc_ids: ids.join(',') } })
    return
  }
  router.push({
    name: 'ScmDocNew',
    query: ids.length === 1
      ? { doc_type: actionState.value.push.targetType, source_doc_id: ids[0] }
      : { doc_type: actionState.value.push.targetType, source_doc_ids: ids.join(',') },
  })
}
```

（其他类型 PO/PQ/SQ 的多源下推保持原逻辑不变）

### 4. 修复 `buildSalesDispatchLines`（`client/src/utils/scmSalesDispatch.ts`）

新增 `useStockLimit` 参数控制是否按库存限制；保留默认 `false` 以兼容现有单订单 `StockDispatch.vue` 流程和既有单测（`scmSalesDispatch.spec.ts`）：

```ts
export function buildSalesDispatchLines(
  rows: SalesDispatchAvailabilityLine[],
  fallbackWarehouse = '',
  options: { useStockLimit?: boolean } = {},
): Partial<ScmDocLine>[] {
  const useStockLimit = options.useStockLimit ?? false
  return rows
    .filter(row => {
      if (useStockLimit) {
        // 按库存限制：只带入库存可发的行；库存为 0 的行整行跳过
        return (Number(row.ship_qty) || 0) > 0
      }
      return (Number(row.base_remaining ?? row.remain) || 0) > 0
    })
    .map(row => {
      const orderRemain = Number(row.base_remaining ?? row.remain) || 0
      const qty = useStockLimit
        ? Math.min(orderRemain, Number(row.ship_qty) || 0)
        : orderRemain
      // ... 其余字段映射不变
    })
}
```

> 注：新预览页 `MultiDispatch.vue` 不一定需要 `buildSalesDispatchLines`（因为它自己构造 `lines`），此修复主要是为后续从 `DocForm.vue` 的合并下推路径（仍存在）一并修正默认行为时使用。本次实现以**预览页直接构造 `lines`** 为准，最小改动 `buildSalesDispatchLines` 仅作为可选增强。

### 5. 后端 `POST /scm/docs` 支持 `source_doc_ids`（如尚未支持）

`MultiDispatch.vue` 生成的请求体为 `{ doc_type: 'SO', source_doc_ids: [id1, id2], partner_code, warehouse_code, lines }`，每行带 `source_line_id`。需确认 `server/src/routes/scmDoc.ts:858` 的 POST handler 已正确处理多源头 `source_doc_ids`（行级 `source_line_id` 是真正的溯源键，表头 `source_doc_id` 在多源场景留空即可，与 `DocForm.vue:loadSourceDocs` 的处理一致）。
