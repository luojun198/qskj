## 二、P0 缺陷（数据损坏 / 金额错误 / 崩溃 / 安全）

### P0-1　现金流量表父子科目双重展开，金额约 2 倍　【已人工确认 ✔】
- **文件**：`server/src/services/staticCashFlowExpand.ts:23`、消费方 `server/src/routes/reportCashFlow.ts:151`、`server/src/services/cashFlowTrialBalance.ts:353`
- **根因**：`expandFlowAccountCodes` 用 `code === prefix || code.startsWith(prefix)` 同时返回父科目（如 1002）**和**其子科目（100201、100202）。而 `getBatchBalances`/`getBatchPeriodRangeSums`（reportBalance.ts:294 `expandTopCodesToLeafIds`）会把每个传入编码**再展开成叶子子树求和**。调用方 `for (code of cashAccountCodes) beginCash += map.get(code)` 于是把 1002 子树算了两遍。
- **证据链**：reportCashFlow.ts:131-154 遍历 `cashAccountCodes`（含父+子）累加 `getBatchBalances` 返回值（父=子之和），实测 data/finance.db 中 1002 存在 100201/100202 子户。
- **后果**：静态现金流量表期初/期末现金 = 实际 2 倍；经营/投资/筹资各行凡映射科目有子科目均翻倍；勾稽两侧同时翻倍反而"看似通过"，用户拿到 2 倍报表。
- **改进**：`expandFlowAccountCodes` 只返回配置前缀本身（叶子展开交给 getBatch*），或改为只返回叶子科目并让 getBatch* 精确匹配；改后对现金流量表全表逐行回归金额。

### P0-2　固定资产处置生成凭证必然崩溃（`voucherRes` 未声明）　【已人工确认 ✔】
- **文件**：`server/src/services/assetDisposal.ts:106`
- **根因**：`voucherRes = vid` 对**从未声明**的变量赋值（全文件仅此一处出现）。server 为 ESM（`server/package.json` `"type":"module"`，tsx/esm 启动，模块严格模式），运行时抛 `ReferenceError`，且在 `db.transaction(()=>{...})()` 内 → 事务回滚。
- **后果**：前端勾选"生成凭证"处置任一资产（`generateVoucher=true`）→ 接口 400，**处置+凭证功能整体不可用**。
- **改进**：删除该行赋值（`vid` 已直接用于 UPDATE），或函数顶部 `let voucherRes: string | null = null` 并把 voucherId 放入返回值供路由响应。

### P0-3　SCM 反审核回退按"仓库+物料"去重，同键仅回退第一条移动　【已人工确认 ✔】
- **文件**：`server/src/services/scmCosting.ts:114-137`
- **根因**：`reverseDocMoves` 用 `removed` Set 以 `warehouse|item` 为键去重（`if (removed.has(key)) continue`），同一单据中同仓同料的**第 2 条及以后** stock_move 被跳过、不回退数量/金额；但末尾第 137 行 `DELETE` 把该单**全部**流水删除，差额永久丢失。
- **后果**：出库/入库单同一物料同仓拆多行，反审核只回退一行，其余数量与金额凭空蒸发，即时库存与账面永久失真且无流水可追。
- **改进**：删除 `removed` 去重，逐条 move 按方向反向增减；或按 (仓,料) 先 SUM 全部 in/out 增量再一次性回冲。

### P0-4　结转/自动转账取数只含"年初+本期净额"，漏 1~N-1 期发生额
- **文件**：`server/src/services/autoTransfer.ts:397`（`PERIOD_END_BALANCE_SQL`）、`getChildrenBalances`
- **根因**：仅取 `account_balances` 中 `period=当期` 的行（init_balance=年初、current_*=本期发生额），未累计本年前几期。代码内 FIX-006 注释已声明该口径不可靠、账簿已改动态计算，但结转仍用旧口径。
- **后果**：费用科目 1 月发生未结转、2 月无发生额 → 2 月结转取数为 0，损益无法清零；利润表错误，年结被损益校验卡死。
- **改进**：SUM 条件改 `ab.period <= ?` 累计，或复用账簿动态期末余额（init_balances 年初 + 截至本期累计借贷净额）；`getChildrenBalances` 同步改。
- 备注：置信度高，逻辑与 FIX-006 注释自相印证；建议改后用一个跨期未结转账套回归。

### P0-5　辅助明细账"期初合计"凭证部分恒为 0（临时表条件互斥）
- **文件**：`server/src/routes/ledger.ts:1533`
- **根因**：`_tmp_aux_detail_ids` 按 `withRangeDate:true` 收集，start_date 存在时所有分录 `voucher_date >= start_date`；`initSqlAll` 又限定 `voucher_date < start_date`，两条件交集为空，SUM 恒 0。期初只剩 init_balances 辅助行，漏掉全部期初前凭证累计。
- **后果**：辅助项目跨月查询时，AuxDetail.vue 余额列从错误期初递推、整列金额错误；且与单独查询的 `categoryInitBalances` 互相矛盾。
- **改进**：期初合计改用 `categoryInitBalances` 同法（按类目 `buildAuxItemMatchCondition` + `voucher_date < start_date` 的 DISTINCT ve.id 求和），或收集临时表时不加 `>= start_date` 下限、期初再过滤。

### P0-6　借贷平衡校验可被客户端伪造的 `amount_cents` 绕过　【已人工确认机制 ✔】
- **文件**：`server/src/services/voucherEntry.ts:140-146`
- **根因**：`getEntryAmountCents` **优先信任请求体的 `amount_cents`**（判平衡用它）；而入库 `buildVoucherEntryPayloads:336-337` 按 `entry.amount` 重新 `yuanToCents`。两者不一致时"校验与存储脱节"。
- **后果**：构造 `[借 amount=1, amount_cents=10000] / [贷 amount=100, amount_cents=10000]` → 平衡校验通过，实际入库借 1 元/贷 100 元，生成借贷不平凭证并可审核记账，总账失衡。（正常前端不触发，但服务端无二次防线。）
- **改进**：`getEntryAmountCents` 不再信任客户端 `amount_cents`，一律 `yuanToCents(entry.amount)`；或在校验时断言 `amount_cents === yuanToCents(amount)` 否则 400。

### P0-7（安全）已审核凭证可经普通修改接口篡改，绕过审核内控
- **文件**：`server/src/routes/voucher.ts:983`
- **根因**：`PUT /vouchers/:id` 仅 `isPostedVoucher` 拦已记账，**不拦 `status='audited'`**。已审核未记账凭证可被仅有 `voucher:entry` 权限的制单人改金额/科目/日期，绕过 `/edit-audited` 的 `requireAllPermissions` 与"制单人≠审核人"控制。同一接口还缺"目标期间已结账"校验（POST/insert/edit-audited 均有）。
- **后果**：内控失效；配合"已审核凭证可直接删除"（见 P1）审计链可被破坏。
- **改进**：`PUT /vouchers/:id` 增加 `if (voucher.status !== 'draft') return 400`（走 /edit-audited）；并补期间结账校验。

## 四、P2 缺陷（健壮性 / 次要口径 / 权限点缺失）

摘录（完整清单见原始评审数据）：

## 五、跨模块主题（根因归类）

1. **多账套隔离普遍缺失**：大量"按 id"写接口不带 `account_set_id`，是本系统最系统性的越权面。**建议统一封装** `getByIdScoped(table,id,accountSetId)` 与"写操作强制附加 account_set_id"的约定/中间件。
2. **ESM 迁移遗留**：`require()`（voucherBatch）、未声明变量严格模式报错（assetDisposal）。**建议**：开启并跑通 `tsc --noEmit`，把这类运行时错误提前到构建期（当前疑似构建未开类型检查，cashFlowReconciliation 缺字段也未报错）。
3. **金额/现金科目硬编码与口径不一致**：现金流父子双计、结转取数口径、间接法/直接法 month vs ytd、AR/AP 兜底科目 1131/2121 vs 1122/2202、出纳硬编码 1001。**建议**建立单一"科目余额/发生额取数"权威函数并全模块复用，杜绝各处自行 SUM。
4. **事务原子性不齐**：SCM 反审核未包事务（审核侧包了）。**未覆盖的横切扫描需补做**，全面排查多步写库。
5. **反审核/删除的可逆性与联动**：SCM 库存回退去重丢数、出纳删除已对账记录不联动、银行对账批次撤销粒度过粗——反向操作普遍缺少与正向对称的完整回退。
